# OKX 到 LLM 的事实契约

## 目标

系统不会把 OKX API 的原始 JSON 整包塞给模型。那样既浪费上下文，也会把张数、币量、空值、旧快照和不完整分页混成看似精确的事实。

正确口径是：交易所原始响应先经过账户绑定、环境绑定、单位归一、源时间校验、分页完整性和财务完整性检查，再投影成带证据 ID 的决策事实。模型只消费这层结构化事实；不满足条件的字段必须显示为“不可确认”，不能补 0，也不能推断为“没有”。

## 进入模型的决策事实

| 事实域 | 来源 | 进入模型的字段 | 关键校验 |
|---|---|---|---|
| 行情 | OKX ticker | 现价、24h 高低、24h 涨跌、交易所源时间、接收时间 | 源时间与接收时间都新鲜；拒绝倒序和未来时间 |
| K 线 | OKX candles | 闭合 K 线数量、最新闭合时间、收盘价 | 只用已闭合 K 线；时间与 OHLCV 质量通过 |
| 微观结构 | funding、OI、order book | 资金费率、OI、点差、深度、盘口失衡及各自源时间 | 每类事实独立 TTL；缺失不转成 0 |
| 合约规格 | instruments | `ctVal`、`minSz`、`lotSz`、`tickSz` | 全部严格有限且大于 0 |
| 交易者结构 | OKX 公共统计 | 大户/散户多空比、主动买卖比 | 仅作补充证据，不替代硬事实 |
| 私有账户 | balance、positions | 净值、可用保证金、方向、张数、币量、开仓/标记/强平价、UPL、杠杆、保证金模式 | 同账户、同 API Key 指纹、同 production/demo 环境；张数必须用 `ctVal` 换成币量 |
| 普通挂单 | orders-pending | 方向、仓位方向、类型、张数、价格、reduce-only、状态 | 分页必须耗尽；不完整时不得声称“无挂单” |
| 策略单 | orders-algo-pending | 止损/止盈类型、触发价、张数、方向、reduce-only、状态 | 分页必须耗尽；用于证明保护是否真的存在 |
| 财务/风险预算 | OKX 快照、成交与账单派生 | 今日盈亏、未实现盈亏、剩余日亏额度、日亏上限 | 成交费、资金费与开放仓事实完整；未对账时整体不可作为精确预算 |

## 模型必须遵守的边界

1. `fresh/passed` 才能写成当前事实。
2. `stale/missing/error/incomplete` 必须明确写“不可确认”。
3. 方向、因果、支撑阻力和行情解释属于判断，不得冒充 API 原始事实。
4. 普通挂单与真实持仓必须分开；策略单与普通单必须分开。
5. OKX 永续 `pos/sz` 是合约张数；币数量只能由 `contracts × ctVal` 得到。
6. `net_mode` 的负持仓必须规范为 short，不能因为原始数量为负而判成“无仓”。
7. API Key 指纹、账户 ID 或 production/demo 环境任一不匹配，私有事实整体拒绝进入模型。
8. API Secret、Passphrase、Bearer Token 和原始敏感请求永远不得进入模型上下文。

## 对“所有 API 数据”的准确表述

系统追求的是“所有对当前决策有用且能证明完整性的 OKX 事实被准确投影”，不是“把 OKX 能返回的每个字段都喂给 LLM”。未被当前决策消费的原始字段可以留在受控证据/审计层；未来新增字段时，必须先定义单位、源时间、完整性和用途，再加入模型事实契约。
