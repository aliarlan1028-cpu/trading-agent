# Kordyn 全系统 UI/UX 重构设计规格

- 日期：2026-08-19
- 状态：对话设计已确认，等待书面规格复核
- 路径：Architectural
- 视觉方向：A「精密纸面」
- 导航方向：A「操作轨道」

## 1. 背景与目标

本次工作从零重构 Kordyn 的产品界面、信息架构和交互方式。旧界面的视觉语言、页面布局与组件组织不作为新设计依据；现有系统功能、真实数据、安全控制和业务闭环仍是设计的唯一功能基础。

新设计参考 `https://e2pdao.xyz/club/` 的视觉气质，包括暖纸色背景、近黑高对比区域、酸性绿色强调、细网格、硬边界和编辑式排版，但不复制参考站点的页面结构或品牌表达。

目标如下：

1. 将复杂交易系统组织成清晰、稳定、可追溯的操作环境。
2. 让普通订阅用户快速理解结论、风险和下一步操作。
3. 让 Owner 在同一信息架构中获得系统健康、证据、模型、Agent、审计和订阅管理深度。
4. 保持桌面端与移动端完整功能对等。
5. 明确区分候选信号、AI 复核、交易计划、风险校验、授权、执行和复盘。
6. 保留后端 API、AI 决策、硬风控、执行器、权限和审计语义。

## 2. 非目标与硬性边界

本次重构不做以下事情：

- 不重新设计交易策略、机会算法或风险规则。
- 不改变后端 API 和核心数据结构的业务语义。
- 不允许前端绕过授权、风控、真实性守卫或执行审计。
- 不以静态假数据替代系统真实状态。
- 不为桌面端和移动端维护两套能力不同的产品。
- 不继续使用旧视觉方案，也不要求安装或使用 Figma。

如果实施期间发现现有 API 无法支持已经存在的功能，先记录缺口；任何后端语义扩展都必须作为独立变更处理，不能隐式混入视觉重构。

## 3. 产品原则

### 3.1 事实先于装饰

页面首先回答“系统现在是什么状态、为什么、下一步能做什么”。视觉层级必须来自业务重要性，而不是平均分配的卡片。

### 3.2 决策必须可追溯

AI 的事实、推断、建议和待授权操作需要明确区分。交易相关结论必须能回到来源、更新时间、计划、风控结果和审计记录。

### 3.3 安全状态不能被弱化

风险阻断、服务降级、数据过期和执行失败必须是独立状态，不得显示成普通空页面或短暂提示。

### 3.4 同一功能，一套产品

桌面端与移动端共享路由、数据、组件、权限和操作。响应式布局只改变信息排列方式，不改变功能范围。

## 4. 整体信息架构

### 4.1 全局应用骨架

全局状态栏始终提供：

- 全局搜索
- OKX 连接状态
- 当前有效运行模式与运行状态
- 通知
- 语言切换
- 账户入口
- Flatten All
- Kill Switch

Flatten All 和 Kill Switch 在所有工作区保持可达。它们的视觉优先级高于普通导航，但不得因高可见性而绕过二次确认和结果反馈。

### 4.2 六个工作区

| 工作区 | 子页面与功能 |
| --- | --- |
| AI Trader | 对话、情报、观察哨 |
| Trading | 总览、市场、持仓、执行、交易复盘、Owner 优化、订单与成交 |
| Research | 知识、策略、能力与工具 |
| Risk | 风险态势、授权 Mandate、风险规则 |
| Ops | 系统健康、事件、任务、审计、通知 |
| Settings | 设置总览、环境与服务、网络代理、数据与备份、登录与凭证安全、OKX、通知、模型与密钥、Agent、用户、订阅 |

用户和订阅管理属于 Owner 权限。Owner 优化属于 Trading 中的 Owner 能力。无权限用户看到清楚的权限说明和获取条件，不能只得到无解释的禁用控件。

### 4.3 桌面导航

桌面端使用持久左侧“操作轨道”：

- 六个工作区固定在一级导航。
- 当前工作区具有强识别状态。
- 工作区内部使用本地标签或本地导航，不把所有子页面塞入全局侧栏。
- 页面标题区统一显示工作区编号、任务标题、本地导航和主要操作。

### 4.4 移动导航

移动端底部导航为：

1. AI
2. Trade
3. Research
4. Risk
5. More

More 提供 Ops 和 Settings。进入工作区后，所有子页面通过工作区标题区和本地导航访问。移动端不得删除、简化或隐藏桌面端已有的业务动作。

### 4.5 首次进入与恢复

- 返回用户恢复上次访问的工作区和子页面。
- 首次进入的普通订阅用户默认打开 AI Trader。
- 首次进入的 Owner 默认打开 Trading 总览。

### 4.6 全局搜索

搜索只覆盖系统中真实存在并可访问的对象：市场、持仓、交易计划、知识、策略、任务、审计记录和功能入口。结果按对象类型分组，并遵守租户和角色权限。

## 5. 页面模板

所有页面从以下模板组合，不再使用无差别卡片墙。

### 5.1 Overview

用于工作区入口。先展示健康状态、需要处理的事项和关键事实，再提供下钻入口。

### 5.2 Workbench

用于交易执行、风险配置等复杂任务。桌面端由主操作区和证据/参数/控制侧栏构成；移动端按任务顺序纵向堆叠，次级内容进入详情页或底部面板。

### 5.3 Registry

用于知识、策略、订单、成交、任务和审计等对象。包含搜索、筛选、排序、列表和详情。移动端将宽表格转换为可排序列表和逐行详情，不丢失字段。

### 5.4 Conversation

用于 AI Trader。对话是任务入口，当前计划、运行状态、证据和风险事实构成伴随上下文。桌面端可使用证据侧栏；移动端使用独立详情层。

### 5.5 Timeline / Trace

用于把候选信号、AI 决策、授权、风控、执行、成交和复盘串成时间事实链，也用于事件和审计追踪。

### 5.6 Settings

由分类索引、范围明确的表单、影响说明和验证结果组成。保存动作必须说明变更作用域、生效状态和失败原因。

## 6. 视觉系统

### 6.1 视觉方向

采用 A「精密纸面」：以暖纸色工作区承载高密度信息，使用近黑色面板突出决策、执行和风险，以酸性绿色表达选中、授权和待行动状态。

建议基础令牌：

| 语义 | 建议值 | 使用范围 |
| --- | --- | --- |
| Canvas | `#F4F1E9` | 全局暖纸色背景 |
| Ink | `#111311` | 主文字、近黑决策面板 |
| Accent | `#CCFF3D` | 当前选中、已授权、需要行动 |
| Healthy | 柔和薄荷绿 | 健康、通过、在线 |
| Warning | 琥珀色 | 降级、警告、需要复核 |
| Danger | 高可读红色 | 阻断、止损、破坏性操作 |

最终颜色在实现中需要通过对比度测试微调，但不得改变上述语义分配。

### 6.2 形态与层级

- 使用 1px 细边框和 0–4px 小圆角。
- 背景可使用极细、低对比度网格。
- 不使用玻璃拟态、大面积渐变和装饰性光晕。
- 阴影只用于浮层、模态和需要脱离文档流的内容。
- 大标题只出现在工作区和页面层级，内部信息保持紧凑、可扫描。
- 近黑面板仅用于高重要性决策、执行、风险或需要立即处理的状态，不能泛滥到普通内容。

### 6.3 字体与数据

- 普通文字使用高可读无衬线字体。
- 状态、时间、ID、价格、数量和市场数字使用等宽字体。
- 数字对齐并保持单位明确。
- 状态不能只依赖颜色，必须同时包含文本或图形标记。

## 7. 核心业务流程

### 7.1 正确的机会链路

系统存在两种入口，并在 AI 决策阶段汇合。

**信号驱动：**

`市场监测发现候选信号 → AI 复核与机会确认 → 结构化交易计划 → 证据与风险校验 → 用户授权 → 执行 → 持仓监控 → 复盘 → 知识沉淀`

前置机会引擎、快速异动、观察哨和新闻只产生候选信号或复核触发，不代表已经确认交易机会。

**AI 直接驱动：**

`用户主动发起／定时巡检 → AI 分析并识别机会 → 结构化交易计划 → 证据与风险校验 → 用户授权 → 执行 → 持仓监控 → 复盘 → 知识沉淀`

界面统一使用以下语义：

- Candidate Signal：候选信号，尚未经过完整 AI 复核。
- Analyzing：AI 正在分析。
- Qualified：已形成计划并通过当前阶段的风险校验。
- Rejected：AI 或风险校验拒绝。
- Watching：证据不足或条件未满足，继续观察。
- Expired / Superseded：候选已过期或被新结构取代。

这些是界面语义层；实现时应映射现有后端状态，而不是擅自改写后端生命周期。

### 7.2 AI Trader

- AI 输出明确区分事实、推断、建议和待确认操作。
- 交易建议展示数据时间、证据来源、风险限制和计划状态。
- 聊天内容不能直接改变账户状态，必须进入既有授权与执行链。
- AI 没有形成真实交易计划时，界面不得暗示计划已经创建或提交。

### 7.3 交易与风险

- 执行前集中展示方向、数量、价格类型、预估敞口、止损和风险结果。
- 风险结果分为通过、警告和阻断；阻断必须说明具体规则与解除条件。
- Flatten All 和 Kill Switch 显示影响范围、当前状态、确认过程和最终结果。
- 执行结果直接关联订单、成交、持仓和审计记录，不能只显示瞬时 Toast。

### 7.4 复盘与知识闭环

- 每次交易将建议、授权、风控、执行、成交和结果串成可追溯记录。
- 复盘结论可转为知识或策略候选，但保留来源、审核和生命周期状态。
- AI 后续引用知识时能够回到原始交易、证据和更新时间。

## 8. 角色自适应

Owner 和普通订阅用户使用同一信息架构。

普通订阅用户默认优先看到：

- 当前结论
- 主要证据
- 风险状态
- 下一步可执行动作

Owner 在相同页面额外获得：

- 更完整的证据与追踪链
- 系统健康与运行状态
- 模型路由和 Agent 行为
- 审计与运营信息
- Owner 优化、用户和订阅管理

角色差异通过信息密度、可见证据和允许操作表达，不能复制两套页面。直接访问无权限路由时，页面显示权限原因和所需权限，不泄露受限数据。

## 9. 响应式与功能对等

桌面和移动使用同一路由、组件、数据请求、权限判断和动作处理。

| 桌面模式 | 移动模式 |
| --- | --- |
| 多栏工作区 | 按任务顺序纵向堆叠 |
| 固定证据或控制侧栏 | 详情页或底部面板 |
| 宽表格 | 可排序列表与逐行详情 |
| 左侧操作轨道 | 底部一级导航 |
| 页面内横向标签 | 可滚动本地标签或子页面选择器 |

只有确实需要横向比较的大型数据集可以横向滚动。移动端必须保留相同字段、精确状态、证据、确认步骤和审计反馈。

## 10. 前端技术架构

### 10.1 单一响应式应用

逐步移除独立桌面页面树和 `MobileApp` 页面树之间的能力分叉，最终由一套响应式应用承载两端。断点只控制布局，不控制业务功能是否存在。

### 10.2 模块边界

前端分为以下边界：

1. **Design System**：颜色、排版、间距、状态、基础控件。
2. **App Shell**：全局状态栏、操作轨道、移动底栏、工作区标题。
3. **Workspace Modules**：六个工作区各自拥有清晰入口和本地页面。
4. **Domain View Models**：把 API 和快照数据转换为页面状态；业务判断不散落在展示组件中。
5. **Safety Interaction Layer**：统一处理授权、风险阻断、危险操作确认和结果反馈。

模块应保持单一职责。工作区页面不能继续无限扩张为一个包含路由、取数、业务判断和视觉渲染的巨型文件。

### 10.3 共享组件

核心共享组件包括：

- `AppShell`
- `GlobalStatusBar`
- `OperatingRail`
- `MobileNavigation`
- `WorkspaceHeader`
- `LocalNavigation`
- `StatusChip`
- `MetricStrip`
- `ActionPanel`
- `DataRegistry`
- `EvidenceTrace`
- `SafetyConfirm`
- `StateBoundary`

组件名称可在实施计划中按现有代码约定调整，但职责边界必须保留。

## 11. 数据与动作流

读取路径：

`现有 API／实时快照 → Domain View Model → 工作区状态 → 页面模板与组件`

动作路径：

`用户动作 → 权限检查 → Safety Interaction Layer → 现有 API → 服务端结果 → 快照协调 → 页面反馈与审计引用`

交易、Flatten All、Kill Switch 和安全配置变更不得使用“先显示成功、失败再回滚”的乐观成功模式。界面只有收到可验证的服务端结果后才能显示成功。

## 12. 状态与错误处理

每个业务页面必须覆盖：

- 首次加载
- 后台刷新
- 正常
- 无数据
- 数据过期
- 服务降级
- 权限不足
- 操作失败
- 操作成功

规则如下：

- 后台刷新保留已有内容，不闪回骨架屏。
- 数据过期保留最后一次有效值，同时展示来源、更新时间和可信状态。
- 服务降级说明受影响能力和仍可使用的能力。
- 无数据与加载失败使用不同表达。
- 危险操作失败展示真实服务端结果、可安全重试方式和审计编号。
- 网络恢复后重新协调服务端状态，不能凭本地假设判定交易结果。

## 13. 迁移策略

按工作区建设，最终统一切换：

1. 建立设计令牌、共享状态语义和应用骨架。
2. 重建 AI Trader 与 Trading 核心链路。
3. 重建 Research、Risk、Ops 和 Settings。
4. 合并移动与桌面页面体系，消除能力分叉。
5. 完成功能映射审计和视觉验收。
6. 删除被新系统替代的旧视觉组件与样式。

每个旧入口必须记录以下映射：

`旧功能入口 → 新工作区 → 新子页面 → 桌面位置 → 移动位置 → 角色权限 → 验收用例`

在映射完整、测试通过前，不删除旧功能代码。旧视觉代码只在确认已被替代后移除。

## 14. 测试与验收

### 14.1 功能验收

- 六个工作区及全部子页面均可访问。
- 现有功能映射不存在无入口能力。
- Owner 和普通订阅用户的权限、数据范围与信息密度正确。
- 桌面和移动拥有相同业务动作和状态反馈。
- 候选信号、AI 复核、交易计划、风险、授权、执行和复盘状态表达准确。
- 所有高风险操作保留确认、服务端反馈和审计链。
- 所有页面使用真实 API 或真实空/错状态，不使用演示数据冒充结果。

### 14.2 自动化测试

- 保持现有测试通过。
- 增加工作区路由和子页面覆盖测试。
- 增加 Owner / 订阅用户角色矩阵测试。
- 增加桌面 / 移动关键动作对等测试。
- 增加候选信号到 AI 复核、计划、风险和授权的展示状态测试。
- 增加 Flatten All、Kill Switch 和交易确认的安全回归测试。
- 增加加载、过期、降级、失败和权限不足状态测试。

### 14.3 视觉与可访问性验收

- 至少在 390px、768px、1280px 和 1440px 宽度逐页检查。
- 检查键盘导航、焦点可见性、文本与状态对比度。
- 移动触控目标不小于可安全操作的尺寸，关键操作避免紧邻误触。
- 状态不只依赖颜色。
- 复杂表格在移动端可完整查看所有字段。
- 页面不存在无意义横向滚动、遮挡或操作栏溢出。

## 15. 完成定义

只有同时满足以下条件，UI/UX 重构才算完成：

1. 新视觉系统覆盖所有工作区，而不是只完成首页或样板页。
2. 旧功能全部映射到新入口，或经明确批准后废弃。
3. 桌面与移动功能对等通过测试和逐页核验。
4. 安全关键操作经过端到端验证。
5. 现有自动化测试与新增 UI 测试通过。
6. 旧视觉代码和独立移动能力分叉完成清理。
7. 无占位文案、演示状态或未解释的禁用控件。
